# 直播可靠性、OBS 联动与程序化头像能力升级

这组改动同时推进直播会话可靠性、OBS WebSocket v5 联动和程序化头像能力诚实化：事件入口被收敛，停播按资源隔离清理，广播与业务队列增加背压，OBS 获得状态/RPC 接口，头像增加文本 Viseme 与能力声明。新增定向测试全部通过，但生产主路径仍有阻塞问题：P0 打断会关闭整场队列消费者，正式房间仍默认启用假弹幕，OBS 所有权可能跨场残留。第三阶段只完成兼容别名和程序化 Viseme；两个扩展驱动仍是空实现，却声明完整能力。  
Watch for: **confirmed** — P0 打断会永久退出主消费循环；**confirmed** — 正式平台熔断仍默认注入 Mock；**confirmed** — P1/P0 可突破队列总容量；**confirmed** — OBS 所有权会在断连场景跨会话残留；**confirmed** — Live2D/Neural 空驱动虚报能力；**confirmed** — Douyin 未接入新增健康状态；**likely** — OBS 控制面在非本机部署下扩大了未授权控制与内网连接面。

**Verdict**: NEEDS_CHANGES

## High-level view

第一阶段部分完成。`stop()` 异常隔离、任务收敛、统一事件入口、按客户端隔离的 WebSocket 队列、同优先级 FIFO、低优先级 TTL、`speaking_state` 的 `finally` 复位和音频代际 fence 已进入生产路径；但 P0 的“真取消”取消了整个消费 worker。队列也只对 P2/P3 有界，P1/P0 在高优消息堆满时仍会扩容。

弹幕健康与熔断只完成一半。Bilibili 报告连接/心跳，Douyin 只报告错误；错误又会经健康回调和错误回调重复计数。半开探测失败会停在 `HALF_OPEN`，正式房间也没有关闭默认 Mock fallback。

第二阶段建立了 OBS v5 握手、认证、RPC、输出指标、控制 API 和本地会话联动，并尝试用 `obs_stream_started_by_agent` 区分所有权。联动启动失败不参与开播事务；所有权也只有在“仍连接且仍推流”时才清除，异常断连可把所有权带入下一场。

第三阶段实现二维口型、文本 G2P 时间线、随机眨眼与机器可读能力，并用别名暴露 `ProceduralAvatarDriver`。原类、文件、全局对象和日志仍沿用 MuseTalk；新增 Live2D/Neural 类没有渲染行为，却声明 Viseme、表情、头动甚至神经口型可用。

## P0 真取消误杀整场消费 worker

**引入的回归（confirmed）**：`_speak_sentence()` 把 `current_tts_task` 设置成 `asyncio.current_task()`，实际得到长期运行的 `_consume_queue_loop` worker，而不是单句 TTS 子任务（`server/routes/live.py:840-850`）。P0 入队触发 `_on_barge_in()` 后取消该 task（`server/routes/live.py:215-217`）；取消传播到最外层后命中 `except asyncio.CancelledError: break`（`server/routes/live.py:767-768`），本场不再消费队列，刚入队的 P0 自身也不会被处理。

代际 fence、生成器 `aclose()`、各 sink 独立中断和 `speaking_state` 的 `finally` 复位提供了正确的防复活基础（`server/routes/live.py:197-227, 742-745, 807-820, 853-927`）。修复需要把单句合成放进独立、可等待的 task，或只关闭当前生成器/网络流。**取消缺口（confirmed）**：Edge 驱动的 `current_task` 从未被赋值（`server/adapters/media/edgetts_driver.py:19, 50-80`），驱动自身的 interrupt 实际不能取消生成。

## 弹幕健康协议与半开状态机不闭环

**部分实现（confirmed）**：基础抓取器新增 connected、worker、心跳、重连失败和错误快照，Bilibili 在建链和心跳回包时更新状态（`server/adapters/danmaku/base_fetcher.py:8-105`; `server/adapters/danmaku/bilibili_fetcher.py:204-209, 255-259`）。但 Bilibili 在认证回包前就标记健康，巡检也不比较 `last_heartbeat_at` 与当前时间；认证失败或心跳冻结仍会被视为健康（`server/adapters/danmaku/bilibili_fetcher.py:201-209`; `server/adapters/danmaku/circuit_breaker.py:177-184`）。

**未实现（confirmed）**：Douyin 成功建链和发送心跳时没有调用 `on_connection_opened()` / `on_heartbeat()`，只在异常时调用 `notify_error()`（`server/adapters/danmaku/douyin_fetcher.py:164-202`）。健康快照因此始终是 disconnected/worker-dead，巡检会把正常静默房间逐步熔断。

**引入的 bug（confirmed）**：`notify_error()` 先触发健康变化回调，再触发错误回调（`server/adapters/danmaku/base_fetcher.py:75-91`）；熔断器在两处都调用 `record_failure()`（`server/adapters/danmaku/circuit_breaker.py:70-86`），一次断线按两次失败计数。进入半开后，若 `real_fetcher.start()` 抛错，`record_failure()` 只允许从 `CLOSED` 转 `OPEN`，巡检又只处理 `OPEN`，状态永久停在 `HALF_OPEN`（`server/adapters/danmaku/circuit_breaker.py:126-139, 185-202`）。半开前 stop-then-start 避免重复 worker 的方向正确，但状态转移尚未闭环。

## 正式房间仍会生成伪弹幕

**引入的回归（confirmed）**：`enable_mock_fallback` 默认是 `True`，达到阈值后启动 Mock 并转发事件（`server/adapters/danmaku/circuit_breaker.py:26-55, 112-139`）。正式 Bilibili/Douyin 的构造调用没有传 `False`（`server/routes/live.py:423-431`），所以“不注入假弹幕”的注释与实际行为相反。

统一入口会标记这些事件并排除运营指标（`server/routes/live.py:592-640`），避免统计污染；但假观众内容仍进入 LLM、TTS 和直播输出。正式来源必须 fail-closed，Mock 只应由演示房间或明确演示模式开启。

## FIFO/TTL 已落地，但高优队列没有硬上界

**已正确实现**：单调 `seq` 保证同优先级 FIFO，P2/P3 出队时执行 TTL，普通/垫场消息满载时拒绝或驱逐（`server/core/queue/priority_queue.py:35-57, 105-184, 205-213`）。统一入口还返回 accepted、被驱逐 ID 和原因（`server/routes/live.py:628-640, 1329-1380`）。

**未实现（confirmed）**：队列被 P0/P1 填满时，P1 明确继续扩容；P0 找不到低优项时也照常入队。底层 `asyncio.PriorityQueue` 没有 `maxsize`，配置的总容量不是硬上界（`server/core/queue/priority_queue.py:71-79, 148-165`）。P0 独立计数不能阻止无限 P1，也不能阻止超总量后继续接受 P0。

**部分实现（confirmed）**：`event_expired_total` 初始化后从未递增，也没有路由暴露 drop/expiry 指标（`server/core/queue/priority_queue.py:81-85, 205-213`）。TTL 测试先取更高优 P1，没有验证过期 P2 被实际弹出或指标增长（`server/tests/test_p0_reliability_guard.py:77-94`）。

## 会话停止可靠，但 OBS 所有权可跨场泄漏

**已正确实现**：`stop()` 按入口、任务、后台工作、音频、媒体、设备、队列顺序清理，每项有独立超时和错误记录，最终状态无条件复位（`server/routes/live.py:499-577`）。生命周期锁覆盖 `/start` 和 `/stop`，本地资源启动失败也会执行 fail-safe stop（`server/routes/live.py:354-365, 1178-1182, 1254-1258`）。

**引入的 bug（confirmed）**：OBS 所有权只在 owner=true、OBS 仍 connected 且仍 streaming 的分支内清零（`server/routes/live.py:1208-1219`）。Agent 启动推流后若 OBS 断连、退出或自行停流，owner 会带入下一场；用户手动恢复推流后，下一场 stop 可能将其误关。所有权应绑定 session，并在每次停场的 `finally` 无条件清除。

## OBS 自动联动不属于开播事务

**部分实现（confirmed）**：客户端完成 v5 Hello/Identify、挑战认证、RPC future、状态事件和码率/帧指标采集（`server/adapters/obs/obs_client.py:50-110, 142-248`），路由提供连接、状态和推流启停接口（`server/routes/live.py:1263-1318`）。外部发布状态把平台是否真正开播保持为 `None`，没有把 OBS 输出误称为平台验收成功（`server/routes/live.py:1056-1078`）。

**未实现（confirmed）**：`obs_auto_link=true` 时，本地 controller 和数据库场次先提交为 live，随后才启动 OBS；失败只写 warning，接口仍返回成功（`server/routes/live.py:1143-1161`）。若 auto-link 是强约束，应在同一事务失败回滚；若允许部分成功，响应必须返回结构化 degraded 状态和重试信息。

## OBS 控制面缺少部署边界约束

**新增风险（likely）**：`/live/obs/connect` 接受任意 host/port，并把密码留在全局单例；连接、断开和推流启停端点没有访问控制依赖（`server/routes/live.py:1271-1318`; `server/adapters/obs/obs_client.py:25-36`）。服务若使用 `--host 0.0.0.0` 或经代理暴露，调用方可让它连接内网 WebSocket 地址并控制已配置 OBS。应限制 loopback/allowlist，并按部署模型增加认证与来源保护。

## 程序化 Viseme 有真实行为，扩展能力仍虚报

**已正确实现**：二维 `mouth_open`/`mouth_form` 实际改变口型宽度与开度，文本时间线与音频时长对齐，异常时回落声学估计；程序化驱动明确报告 `neural_lipsync: false`（`server/core/media/g2p_viseme.py:8-149`; `server/core/media/procedural_renderer.py:162-190, 249-274`; `server/adapters/media/musetalk_driver.py:228-270, 366-396`）。随机眨眼和运镜提供实际微表情/头动近似。

**部分实现（confirmed）**：`ProceduralAvatarDriver` 和 `Viseme2DMediaDriver` 只是旧 `MuseTalkMediaDriver` 的别名；生产类名、文件名、全局单例与 logger 仍是 MuseTalk（`server/adapters/media/musetalk_driver.py:45-47, 399-403`）。应让程序化类成为主实现，再将 MuseTalk 旧名反向设为兼容别名。

**引入的能力误报（confirmed）**：`Live2DDriver` 的 feed/interrupt 为空，却声明 Viseme、G2P、表情和头动为 true；`NeuralLipSyncDriver` 同样无实现，却声明 neural/viseme/expressions/head motion/remote rendering 全部可用（`server/adapters/media/musetalk_driver.py:405-467`）。这些类当前只在测试中实例化，生产路由没有注册或选择它们；未实现能力应为 false/experimental，或让启动明确失败。

## 测试证明局部机制，未覆盖组合失效

新增 16 项定向测试和 Ruff 检查均通过，覆盖 FIFO、普通背压、基础 TTL、fail-safe 清理、OBS 握手/RPC、Mock 指标隔离、理想所有权、二维口型和能力字典。**测试缺口（confirmed）**：没有覆盖播放中 P0 后 worker 存活、正式房间禁用 Mock、Douyin 正常健康、单次错误计数、半开失败重试、纯高优绝对容量、OBS 断连后的 owner、auto-link 失败事务，以及扩展能力与真实行为一致性。现有熔断测试手工 stop/start，绕过真实 monitor，因此发现不了 `HALF_OPEN` 卡死（`server/tests/test_p0_reliability_guard.py:97-140`）。

## 非三阶段目标的启动器与控制台改动

**范围风险（likely）**：同一 diff 还包含启动器默认 `--restart`、跨盘软件探测、大量控制台布局/CSS 和静态构建产物（`launcher.py:458-605`; `run_agent.bat:64`; `server/routes/system.py:120-737`; `server/static/**`）。批处理现在每次启动都清理历史 launcher 和占用端口的进程，行为影响明显，却不属于三阶段核心目标；`suggestion.md` 也作为未跟踪文件混入。建议拆分后分别验证进程回收和 UI 构建一致性。
