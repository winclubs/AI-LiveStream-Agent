# 本地直播执行链路的可靠性与验收边界审查

当前实现已串起版本化迁移、订单库存流水、角色与场次持久化、整句音频提交、资源预算、Electron 外部 Python 预检、健康探针和停服备份恢复。实际复跑为 132 passed、branch coverage 63.52%，串行主路径成立。阻塞验收的问题集中在并发状态转换和最终媒体输出：控制台商品画层没有进入 OBS 捕获的虚拟摄像头，竖屏帧还会被拉伸成横屏；并发开播和退款也可能产生错误持久状态。Watch for: **[confirmed]** 虚拟摄像头缺少商品画层且改变宽高比；**[likely]** 并发开播可生成幽灵 live 场次；**[likely]** 并发退款可重复回补库存；**[confirmed]** 跨场幂等重放会污染当前场统计。

**Verdict**: NEEDS_CHANGES

## High-level view

优惠券、商品特写和尺码表只作为 WebSocket 事件渲染在 Electron DOM，未合成进程序化渲染帧；720×960 的竖屏帧还会被虚拟摄像头直接缩放到 1280×720。**[confirmed]** 因而本地控制台预览不能代表 OBS 捕获结果。

开播检查、场次提交和资源启动之间没有串行化，两个请求可能都留下 live 记录而控制器只运行一个。**[likely]** 订单扣减和取消有条件状态更新，但退款没有；全局 external_id 重放还会把历史场统计写入当前控制器。**[likely]**

整句 TTS 提交避免了失败半句泄漏，但输出 await 后没有重新检查打断代际，VirtualAudio 也无法识别陈旧音频。**[confirmed]** 容器解码失败后按裸 PCM 播放，会在缺少对应解码能力时输出噪声。**[likely]**

上传有大小和展开预算，但 PDF/DOCX、向量、声学特征和人脸处理仍同步占用 async 服务线程。**[confirmed]** 迁移、探针、日志与停服备份的正常路径有测试，启动初始化失败却绕过统一清理。**[confirmed]**

## 商品画层与虚拟摄像头是两条分离的输出链

优惠券、商品特写和尺码表工具仅广播 WebSocket 事件（`server/core/tools/tool_bus.py:78`, `:94`, `:111`），由 `server/static/js/console.js:519-537` 渲染成 DOM；程序化驱动把未叠加 DOM 的 `frame_rgb` 直接发送给虚拟摄像头（`server/adapters/media/musetalk_driver.py:236-240`）。因此 OBS/直播伴侣捕获不到这些“画层”。现有测试只检查 DOM 元素和函数存在（`server/tests/test_product_context_and_overlays.py:121-137`），没有验证输出帧像素。该 **[confirmed]** 高严重度缺口需要帧内合成，或明确的浏览器捕获源及实际捕获测试。

程序化画布为 720×960（`server/adapters/media/musetalk_driver.py:61-62`），全局虚拟摄像头固定为 1280×720（`server/core/media/virtual_cam.py:27-30`），并直接 `cv2.resize`（`:77-81`）。9:16 画面因此被拉伸成 16:9。该 **[confirmed]** 高严重度缺陷需要统一分辨率或保持比例的 letterbox/crop。

## 开播状态转换缺少单一所有者

`start_live` 仅在入口检查 `is_live`（`server/routes/live.py:795-797`），直到场次已提交后才启动控制器（`:841-849`）。若另一请求抢先启动，`_start_resources` 会直接返回，但后到调用方仍把自己的记录标为 live。两个请求可都返回成功，数据库留下两个 live 记录，而停止只能收敛控制器持有的一个 session_id。该 **[likely]** 高严重度缺陷应以 controller 级 async lock 包住完整状态转换，让竞争请求返回 409。

五轮开停测试（`server/tests/test_operations.py:92-104`）严格串行；需要并发 start 测试断言只有一个成功，且数据库至多一个 live/starting 场次。

## 退款 compare-and-set 与幂等作用域不对称

退款先读取 completed，再直接设置 refunded 并执行库存加法（`server/routes/live.py:1389-1407`）。两个事务都读到 completed 时，第二个请求没有 `rowcount` 门禁阻止重复回补和重复流水。该 **[likely]** 高严重度缺陷应复用取消订单的条件状态更新，只让状态抢占成功者修改库存。

命中任意历史 external_id 后，代码调用 `_refresh_order_stats(db, existing.session_id)`（`server/routes/live.py:1280-1284`），该函数写入当前全局控制器 stats。旧场请求在新场重放会把仪表盘替换成旧场聚合值。该 **[confirmed]** 中严重度错误应避免在历史重放时改写当前场，或把幂等作用域定义为 `(session_id, external_id)`。

## 音频代际没有贯穿三路输出

`_speak_sentence` 在 `server/routes/live.py:651-675` 检查代际，然后 `await global_media_driver.feed_audio_chunk`，再输出到 VirtualAudio 和 WebSocket（`:685-688`）。P0 打断落在这个 await 内时，后两路仍收到旧音频；浏览器可能按代际丢弃，但 VirtualAudio 队列没有 generation。该 **[confirmed]** 中严重度缺口需要在让出控制权后复核，并把代际传到物理音频 worker。

`decode_audio_to_float32` 在 soundfile 失败后无条件将同一缓冲解释为 int16 PCM（`server/core/media/audio_decode.py:36-49`）。默认 MP3 在本机 libsndfile 不支持对应编码时会成为噪声。该 **[likely]** 中严重度缺陷应让 codec/container 参与解码，只对明确的 raw PCM 使用 PCM 分支。

## 资源预算限制展开量但没有隔离 CPU 工作

知识上传同步调用提取和 ingest（`server/routes/knowledge.py:110-116`），ingest 循环生成最多 3000 个向量（`server/core/rag/engine.py:418-431`）；音色上传同步提取特征（`server/routes/voices.py:80-88`），头像上传同步检测人脸（`server/routes/avatars.py:69-77`）。接近上限的合法输入或并发上传会阻塞 health、stop 和直播调度。该 **[confirmed]** 中严重度缺陷应移到有并发上限的 worker/to_thread，并测试负载期间 `/readyz` 与 `/live/stop` 延迟。

## 初始化失败未进入停服清理

lifespan 在初始化前写 `.service.lock`（`server/app.py:49-50`），初始化异常在 `:65-69` 重新抛出；锁删除、engine/media 关闭和日志 flush 位于后续 yield 的 finally（`:71-87`），因此启动失败不会进入。该 **[confirmed]** 低严重度运维缺口应使用统一外层 try/finally，并增加迁移失败后的资源清理测试。
